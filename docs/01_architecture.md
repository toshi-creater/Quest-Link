## 3. 技術の選択理由

### 3.1 フロントエンド

**Next.js（App Router）**

SSRによるSEOと初期表示パフォーマンスを確保しつつ、React Server Componentsによりクライアント側のJavaScriptを最小化できる。Vercelへのゼロコンフィグデプロイにより、小規模チームでの運用コストが低い。部屋一覧などの静的寄りのページをキャッシュしつつ、リアルタイムチャットのような動的UIをクライアントコンポーネントとして共存させる構成が自然に表現できる。

**TypeScript**

フロントエンド・バックエンド双方でTypeScriptを使用することで型定義を共有（Zodスキーマを共有ライブラリとしてモノレポ管理）でき、APIの型安全性を一貫して保てる。チーム規模が小さいMVP段階から型の恩恵を受けられる。

**Zustand**

Reduxに比べてボイラープレートが極めて少なく、Socket.IOのリアルタイムイベントをstoreに反映させるシンプルなパターンが書きやすい。部屋の参加者リストや接続状態などのグローバル状態管理に適している。

**TanStack Query**

REST APIへのデータフェッチ・キャッシュ・再取得を宣言的に管理できる。部屋一覧の定期更新（ポーリング）や、評価送信後のキャッシュ無効化などを少ないコードで実現できる。

---

### 3.2 バックエンド

**Fastify**

Expressより高いスループット（ベンチマーク上で2〜3倍）を持ちながら、Expressと同様のエコシステムを利用できる。Zodとの統合プラグイン（`fastify-type-provider-zod`）により、リクエスト/レスポンスのスキーマバリデーションと型推論が同時に完了する。Phase 1のピークRPS 50はもちろん、Phase 2のRPS 500にも単一サーバーで対応可能な性能がある。

**Socket.IO**

WebSocket接続管理・自動再接続・ルームベースのブロードキャストが組み込みで提供されており、ゼロからWebSocketサーバーを構築するより開発コストが大幅に低い。Phase 2以降でRedis AdapterをプラグインするだけでWebSocketサーバーの水平スケールに対応できる設計になっている点が採用の決め手。

**Prisma**

型安全なクエリビルダーによりSQLインジェクションリスクを排除できる。マイグレーション管理が組み込まれており、スキーマ変更の追跡が容易。PostgreSQLの機能（トランザクション、配列型、JSONBなど）を完全にサポートしている。

---

### 3.3 データストア

**PostgreSQL**

ユーザー・部屋・評価データはリレーショナルな構造を持ち、評価の重複チェック（同一セッション内で1人1回）のような整合性制約をDBレベルで保証できる。Supabase経由でホスティングすることで、Phase 1は運用管理コストを最小化しつつ、将来的にRLSやリアルタイムサブスクリプション機能も利用可能になる。

**Redis**

Phase 1ではセッションストアとして使用し、Phase 2以降でSocket.IO Redis Adapterを導入することでWebSocketサーバーの水平スケールを実現する。この段階的な移行計画により、Phase 1では複雑性を抑えながら、Phase 2への移行パスを事前に確保できる。

---

### 3.4 インフラ

**Vercel（フロントエンド）**

Next.jsのホスティングに最適化されており、GitHub連携によるゼロコンフィグデプロイとプレビュー環境が標準で提供される。エッジCDNによる静的アセットの高速配信も自動的に得られる。

**Railway / Render（バックエンド）**

Node.js + WebSocketをサポートしているPaaSとして選定した。AWS / GCPと比較してMVP段階の運用コスト（設定工数・費用）が大幅に低く、コンテナのスケールアウトにも対応している。PaaSとしての制約内で対応できなくなるPhase 2〜3では、ECS / Cloud Runへの移行を検討する。

---

### 3.5 外部API

**IGDB API（ゲーム情報）**

Twitch Developerが提供するゲームデータベースAPI。数十万タイトル以上のゲーム情報（ID・名称・カバー画像・ジャンルなど）を検索・取得できる。ゲームタイトルの自由入力を廃止し、IGDB上のゲームIDで管理することで表記揺れ（例：「Apex」「APEX Legends」「Apex Legends」）を排除し、データの統一性を担保できる。

**認証**: Twitchアカウントと連携したクライアントID・シークレットによるClient Credentials Flowを使用する。取得したアクセストークンはバックエンドのメモリまたはRedisにキャッシュし、期限切れ前に自動更新する。

**キャッシュ戦略**: 取得したゲーム情報はDBの `games` テーブルにキャッシュする（キャッシュ有効期間: 30日）。まず `games` テーブルをキーワード検索し、件数が不足する場合のみ IGDB API を呼び出してキャッシュに追加する。有効期限切れのレコードに検索ヒットした場合は IGDB API から再取得して上書き更新する。

**レート制限**: IGDB API には呼び出し制限（4リクエスト/秒）があるため、バックエンドでリクエストをキューイング・リトライする。

### 3.6 フェーズ移行における技術的考慮点

| フェーズ | 主な変更点 |
|---------|-----------|
| Phase 1 → 2 | Socket.IO Redis Adapterを追加してWebSocketを水平スケール化。PostgreSQLの読み取りレプリカを追加 |
| Phase 2 → 3 | ECS / Cloud Run等のコンテナオーケストレーション基盤へ移行。CDN + APIゲートウェイの導入。DBシャーディングの検討 |
