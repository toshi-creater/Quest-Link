## 1. プロダクト概要

オンラインゲームを「一緒にプレイする相手を探しているユーザー同士」を効率的にマッチングさせるWebアプリケーション。

> 既存のフレンド機能やSNSは「既知の関係」を前提としているが、本アプリは**未知のプレイヤー同士が即時にプレイ仲間を見つけられること**を主目的とする。
>
> ポジション：Discord（募集が分散）とフレンド機能（固定関係）の中間に位置するサービス。

### 1.1 解決する課題

- 一緒にプレイする相手がいない
- フレンドを増やす心理的ハードルが高い
- SNSや掲示板での募集は手間がかかる
- プレイヤーの質が事前に分からない
- 即時にプレイできる相手を見つけにくい

### 1.2 提供価値

| 価値 | 内容 |
|------|------|
| 即時性 | 今すぐプレイできる相手が見つかる |
| 信頼性 | 評価システムにより質の低いプレイヤーを回避可能 |
| 低心理コスト | フレンド登録不要・一時的なプレイ関係 |
| スケーラビリティ | ゲームタイトル非依存・あらゆるオンラインゲームに対応 |

## 2. 認証・アカウント設計

### 2.1 認証方式

| 項目 | 仕様 |
|------|------|
| ログイン方法 | Googleソーシャルログインのみ（MVP） |
| ゲスト利用 | 不可。全機能に認証必須 |
| 将来拡張 | Discord・Twitter/X 等のソーシャルログイン追加 |

### 2.2 初回ログインフロー

```
Googleログイン完了
    ↓
プロフィール設定画面（強制表示）
    ↓
ユーザー名を設定するまで部屋機能は利用不可
    ↓
プロフィール設定完了
    ↓
部屋一覧へ遷移
```

### 2.3 プロフィール項目

| 項目 | 必須／任意 | 備考 |
|------|-----------|------|
| ユーザー名 | 必須 | 重複許可（識別はUser IDで行う） |
| アイコン | 任意 | 未設定時はデフォルトアイコンを表示 |
| 自己紹介 | 任意 | テキスト形式 |
| ゲームタイトル | 任意 | 複数設定可 |
| プレイスタイル | 任意 | カジュアル / ランク重視 / 初心者歓迎 / 上級者限定 |

### 2.4 アカウント管理

- プロフィール編集機能（MVP対象）
- アカウント削除（退会）機能（MVP対象）

## 3. 部屋のライフサイクル管理

### 3.1 ステータス定義

| ステータス | 説明 |
|-----------|------|
| 募集中 | 参加者を受け付けている状態 |
| プレイ中 | 満員になり、自動的に遷移した状態 |
| 終了 | ホストが手動で終了した状態 |

### 3.2 ステータス遷移

```
募集中
  ↓ 満員（最大人数到達）で自動遷移
プレイ中
  ↓ ホストが手動で終了操作
終了
```

**遷移ルールの詳細**

- **募集中 → プレイ中**：満員（最大人数到達）で自動遷移
- **プレイ中 → 募集中**：遷移しない（ホストによる「募集再開」操作の対応は要検討）
- **プレイ中 → 終了**：ホストが手動で終了操作を実行
- **空き部屋の自動クローズ**：設けない（ホストが手動で閉じるまで存続）

### 3.3 ホスト離脱時の挙動

| ケース | 挙動 |
|--------|------|
| 参加者がいる場合 | 最も早く参加したユーザーへ自動引き継ぎ |
| 参加者が0人の場合 | 部屋を自動終了 |
| 引き継ぎ通知 | チャット欄にシステムメッセージを表示（例：「〇〇さんがホストになりました」） |

### 3.4 終了後のデータ管理

- 終了した部屋は一覧から非表示
- 評価完了まで部屋データをDBに保持（評価機能との連動のため）

## 4. 評価システム

### 4.1 評価形式

| 項目 | 仕様 |
|------|------|
| 評価形式 | 1〜5の星評価 |
| 評価対象 | 同室の全参加者（自己評価は除外） |
| 匿名性 | 完全匿名。誰が評価したかは非公開 |
| 変更・削除 | 不可（一度送信した評価は確定） |

### 4.2 評価タイミング・期限

- 評価は**任意**（スキップ可能）
- 退出後**24時間以内**のみ評価可能（期限切れ後は評価不可）
- **リマインド**：次回ログイン時にアプリ内バナーで「未評価のセッションがあります」と通知

### 4.3 スコア集計・表示

| 項目 | 仕様 |
|------|------|
| 集計方法 | 1〜5の単純平均（小数点第1位まで表示） |
| 表示形式 | ★4.2 / 128件 |
| 評価数が少ない場合 | 5件未満は「評価なし」または「評価数が少ないです」と表示 |

### 4.4 不正対策

- 同一セッション内での重複評価を禁止（1人1回のみ）
- 自己評価の排除（システムレベルで制御）

## 5. 主要機能一覧（MVP）

| 機能 | 概要 |
|------|------|
| ユーザー登録・認証 | Googleソーシャルログイン、初回プロフィール設定 |
| プロフィール管理 | ユーザー名・アイコン・自己紹介・ゲームタイトル・プレイスタイルの設定・編集 |
| 部屋作成 | ゲームタイトル・最大人数・プレイスタイルを設定して部屋を作成 |
| 部屋一覧・検索 | 募集中の部屋を一覧表示。ゲーム・プレイスタイル・評価でフィルタ（将来拡張） |
| 部屋参加 | 最大人数未満の部屋に参加。重複参加不可 |
| リアルタイムチャット | WebSocketベース。参加者間でリアルタイムにメッセージ送受信 |
| 部屋退出 | 任意のタイミングで退出可能。退出後に評価画面へ遷移 |
| 評価機能 | 退出後24時間以内に同室参加者を星評価（任意・匿名） |
| 評価表示 | ユーザープロフィールに累積評価スコアを表示 |
| アカウント削除 | 退会機能 |

## 6. 規模・パフォーマンス要件

### 6.1 成長フェーズ別スケール目標

| 指標 | Phase 1（開発初期） | Phase 2（成長期） | Phase 3（拡大期） |
|------|-------------------|-----------------|-----------------|
| MAU | 1万 | 10万 | 100万 |
| DAU | 2千 | 2万 | 20万 |
| ピーク RPS | 50 | 500 | 5,000 |
| 同時接続数 | 100〜500 | 1,000〜5,000 | 10,000〜50,000 |

### 6.2 フェーズ別の特徴と設計上の考慮点

**Phase 1 — 開発初期**

- シンプルな構成を優先し、スモールスタートで検証する
- WebSocketの同時接続は数百規模。単一サーバーでも対応可能な水準
- ピークRPS 50は一般的なVPS・PaaSで十分に捌けるレベル
- まずは動くものを作り、ボトルネックを計測してから最適化する方針

**Phase 2 — 成長期**

- 同時接続が最大5,000に達するため、WebSocketサーバーの水平スケールを検討
- DBへの読み取り負荷が増加するため、読み取りレプリカやキャッシュ層（Redis等）の導入を検討
- ピークRPS 500に備え、ロードバランサーの導入が現実的になるフェーズ

**Phase 3 — 拡大期**

- 同時接続が最大50,000に達するため、WebSocketの接続管理に専用インフラ（例：専用のPub/Subブローカー）が必要になる可能性がある
- ピークRPS 5,000に対応するため、CDN・APIゲートウェイ・マイクロサービス分割を本格検討
- DBのシャーディングや読み書き分離の設計が必要になるフェーズ

### 6.3 設計方針

- Phase 1の構成でも、Phase 2への移行を意識したスケールアウト可能な設計を心がける
- 各フェーズの移行タイミングは、実測値（負荷・レイテンシ・エラー率）をモニタリングしながら判断する
- WebSocketの同時接続管理はリアルタイムチャットの中核であり、早期から負荷試験を実施する

## 7. 未決定事項・今後の検討項目

| 項目 | 内容 |
|------|------|
