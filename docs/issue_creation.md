# GitHub Issue 作成指示プロンプト

## ゴール

Webアプリケーションの実装を成功させるために、以下の方針でIssueを設計・作成する。

1. ユーザー価値が最速で届くMVPを定義する
2. 各Issueを「半日〜1日で終わる粒度」に分解し、AC（受け入れ基準）を明確化する
3. Nice-to-have機能のIssueも作成するが、MVPより優先度を下げる
4. **各Issueに変更対象ファイルと依存関係を明記し、並列実装の判断材料を提供する**

---

## 事前確認（必須）

1. `/docs` 配下の仕様書を確認し、実装対象のWebアプリの概要・技術スタックを把握する
2. MVPのスコープをユーザーと合意してからIssue作成に着手する
3. `gh auth status` で認証済みであることを確認する
4. `gh label list --repo owner/repo` で使用可能なラベルを確認する

---

## 制約

1. **作成前に全Issueの一覧を提示し、承認を得てから実行すること**
2. 1つのIssueは半日〜1日で完了できる粒度にする（大きい場合は分割する）
3. すべてのIssueにAC（受け入れ基準）を必ず記載する
4. 存在確認できていないラベル・アサイン・マイルストーンは使用しない
5. `--repo owner/repo` を必ず明示的に指定する
6. 本文に機密情報・認証情報を含めない

---

## 並列実行グループの設計

Issue一覧を作成する際、以下の手順で**並列実行グループ**を設計する。

### 判定手順

1. 各Issueの「変更対象ファイル」を洗い出す
2. 変更対象ファイルが重複しないIssue同士を**同一グループ（並列実行可能）**にまとめる
3. 以下のいずれかに該当するIssueは**直列（前のグループ完了後に着手）**とする：
   - 他のIssueと変更対象ファイルが重複する
   - 他のIssueの成果物に依存する（DB migration、共通型定義、API定義など）
   - 広範囲のリファクタリングや設定変更を伴う

### 提示フォーマット

全Issue作成前に以下の一覧を提示する：

```
## 作成予定の Issue 一覧

### Group 1（並列実行）
| # | タイトル | 変更対象 |
|---|---------|---------|
| 1 | DB スキーマ定義 | prisma/schema.prisma, src/lib/db.ts |
| 2 | 認証API実装 | src/app/api/auth/**, src/lib/auth.ts |
| 3 | UIレイアウト作成 | src/components/layout/**, src/app/layout.tsx |

### Group 2（Group 1 完了後に並列実行）
| # | タイトル | 変更対象 | 依存 |
|---|---------|---------|------|
| 4 | ユーザーCRUD API | src/app/api/users/**, src/lib/db.ts | #1 |
| 5 | ログイン画面 | src/app/login/**, src/components/auth/** | #2, #3 |

### Group 3（単独実行）
| # | タイトル | 変更対象 | 依存 | 備考 |
|---|---------|---------|------|------|
| 6 | E2Eテスト追加 | tests/**, playwright.config.ts | #4, #5 | 全機能完成後 |

### Nice-to-have（優先度：低、MVP完了後に実行）
| # | タイトル | 変更対象 |
|---|---------|---------|
| 7 | ダークモード対応 | src/styles/**, src/components/** |

---

### 並列実行マップ

Group 1: [#1] [#2] [#3]  ← 同時実行
              ↓
Group 2:    [#4] [#5]    ← 同時実行
              ↓
Group 3:      [#6]       ← 単独実行

上記の内容でIssueを作成してよいですか？
```

## 実行コマンド形式
```bash
gh issue create \
  --repo owner/repo-name \
  --title "タイトル" \
  --body "本文" \
  --label "label1,label2" \
  --assignee "username"
```

---

## Issue 本文構成
```markdown
## 概要

## 実装内容

## 変更対象ファイル
- `path/to/file1.ts`（新規作成 / 変更）
- `path/to/dir/**`（新規作成 / 変更）

## 依存関係
- なし
- または: #XX（Issue タイトル）が完了していること

## AC（受け入れ基準）※必須
- [ ] 
- [ ] 

## 補足情報（任意）
```

---

## 不明な場合に確認すること

| 項目 | 内容 |
|------|------|
| アプリ概要・技術スタック | `/docs` 配下の仕様書を参照。不明点のみユーザーに確認する |
| MVPスコープ | リリースに必須な機能はどこまでか |
| リポジトリ | `owner/repo` の形式 |
| 関連 Issue / PR | 紐付ける番号があるか |

---

## 実行後に報告すること

- 作成された全IssueのURLと番号
- MVP / Nice-to-have の分類サマリー
- 並列実行グループの最終確定マップ
- 実行したコマンド一覧
